# Codex Agent Rules (CatsScreening)

Этот файл задаёт правила работы агента внутри репозитория.

## Язык

- Коммуникация с пользователем: русский язык.
- Комментарии в коде: русский язык, только для неочевидной логики и критичных решений — **что делает** и **почему**. Очевидный код не пересказывать и комментарии ради объёма не добавлять.

## Workflow (обязательно)

- Любая задача выполняется по шагам согласно workflow:
  - `.codex/workflows/skills-workflow.md`
- Каждый шаг фиксируется отчётом в `.tmp/reports/`:
  - маска имени: `step-XXX_<короткое-название>.md`
  - нумерация `XXX` — сквозная, с ведущими нулями (001, 002, …).

## Приоритет: результат без лишнего scope

- Источники требований: прямой запрос пользователя и явно названные им актуальные спецификации.
- Существующий код, старые планы, отчёты, тесты, возможные атаки и гипотетические будущие сценарии сами по себе **не создают новых требований**.
- Перед изменениями обязательно зафиксировать четыре строки: `RESULT`, `IN SCOPE`, `OUT OF SCOPE`, `MODE`.
- Случайно найденные проблемы не расширяют задачу. Исправлять их можно только когда они доказанно блокируют запрошенный результат; иначе достаточно краткой заметки без изменения кода.
- Миграция, обратная совместимость, импорт старых данных и поддержка legacy-формата выполняются только по прямому требованию пользователя. Самостоятельно добавлять их запрещено.

## SOLID, KISS и YAGNI

- **KISS:** сначала использовать самый простой уже существующий механизм проекта.
- **YAGNI:** не добавлять код, слой, dependency, сервис или инфраструктуру «на будущее».
- **SOLID:** разделять только реально разные ответственности и внешние границы. Не создавать интерфейсы, adapters, repositories, engines или дополнительные слои ради самого паттерна.
- Новые dependency, файл конфигурации, сервис, таблица/БД, очередь, worker, storage-механизм или общая абстракция допустимы только при явном требовании и доказательстве, что существующий механизм не решает задачу проще.
- Предпочтение: точечный hotfix существующей архитектуры. Архитектурная замена допустима только если конкретно показано, что без неё нельзя выполнить acceptance criteria.

## Допущения и доказательства

- Для существенных решений различать: `REQUIRED`, `PROPOSAL — NOT APPROVED`, `ASSUMPTION — UNPROVEN`, `OPEN DECISION`.
- Отделять `FACT` (что есть), `REQUIREMENT` (что нужно получить), `RESULT` (наблюдаемое поведение) и `MECHANISM` (как это реализовано).
- Security-изменение вне очевидного минимума требует доказанного пути: актив → граница доверия → источник → sink → ущерб → почему текущей защиты недостаточно. Без этого это недоказанное допущение, а не scope реализации.

## Ограничение масштаба

- Обычная задача выполняется основным агентом без subagents. Допустимы максимум 1–2 независимых read-only потока, только если это действительно сокращает время; общий код они не меняют и дочерних агентов не создают.
- Если один шаг выходит за 8 основных файлов, примерно 1000 строк net diff, 90 минут или требует новой подсистемы, сначала упростить решение. Если упростить нельзя — остановиться и задать пользователю один конкретный вопрос.
- Каждый шаг должен давать один наблюдаемый результат и не порождать новые implementation-шаги из побочных находок.
- Проверки запускать один раз по изменённой поверхности и один итоговый gate; не повторять полный build/test без новых изменений.
- Отчёт шага создавать после получения стабильного результата; отчёт должен быть кратким и не становиться отдельным проектом.

## Исследования (сначала локально, потом интернет)

Перед тем как искать что‑либо в интернете по научной/алгоритмической части:

1. Сначала открыть карту исследований: `docs/research/research-map.md`.
2. Если информации недостаточно — искать в интернете.
3. Если найденный материал нужен проекту “в долгую”:
   - сохранить локальную копию в `docs/research/papers/` (PDF/HTML) или `docs/research/notes/` (если PDF недоступен),
   - обновить `docs/research/research-map.md`, добавив путь к локальной копии и короткую выжимку.

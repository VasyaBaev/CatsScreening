# Workflow выполнения шага (обязательно)

Этот workflow описывает, как агент выполняет **любой** запрос в проекте CatsScreening.

## 0) Выбор номера шага

Перед началом работы:

1. Посмотреть `.tmp/reports/` и найти последний `step-XXX_*.md`.
2. Следующий шаг = `XXX + 1`.
3. Отчёт оформить только после получения стабильного результата; не превращать ведение отчёта в отдельную работу.

## 1) Карточка границ задачи

До исследования и кода зафиксировать ровно четыре строки:

```text
RESULT: какой наблюдаемый результат должен получить пользователь
IN SCOPE: что необходимо изменить для этого результата
OUT OF SCOPE: что сознательно не делаем
MODE: read-only | fast | predeploy | full
```

Правила:

- прямой запрос пользователя и явно названные актуальные спецификации создают требования;
- существующий код, исторические документы, отчёты, тесты и возможные будущие сценарии дают контекст, но не расширяют scope;
- случайно найденная проблема исправляется только если доказанно блокирует `RESULT`; иначе оставить краткую read-only заметку;
- миграция, обратная совместимость, импорт legacy-данных и поддержка старого формата не выполняются без прямого требования.

## 2) Факты, требования и допущения

Для каждого существенного решения разделить:

- `FACT` — подтверждённое состояние кода, данных или среды;
- `REQUIREMENT` — запрошенный результат;
- `RESULT` — проверяемое внешнее поведение;
- `MECHANISM` — минимальный способ реализации.

Неочевидные утверждения помечать как одно из:

- `REQUIRED`;
- `PROPOSAL — NOT APPROVED`;
- `ASSUMPTION — UNPROVEN`;
- `OPEN DECISION`.

Если критической информации нет и безопасное минимальное решение невозможно, задать один конкретный вопрос. Не компенсировать неизвестность дополнительными слоями кода.

## 3) Исследования: сначала локально, потом интернет

Если задача требует научных источников/алгоритмических обоснований:

1. Сначала открыть `docs/research/research-map.md`.
2. Если ответа нет — искать в интернете.
3. Если найденный материал нужен проекту “в долгую”:
   - сохранить локальную копию в `docs/research/papers/` (предпочтительно PDF) или `docs/research/notes/` (если PDF недоступен),
   - обновить `docs/research/research-map.md`: добавить ссылку, путь к локальной копии и краткую выжимку.

## 4) План

- Составить 1–5 коротких шагов, достаточных для `RESULT`.
- Каждый шаг должен давать один наблюдаемый результат, иметь собственную проверку и не порождать новые implementation-шаги из побочных находок.
- Обычную задачу выполнять без subagents. Допустимы максимум 1–2 независимых read-only потока без общих edits и без дочерних агентов, только когда это заметно ускоряет работу.
- Не добавлять отдельные этапы «на всякий случай», «под будущее», для общей перестройки или для необязательного hardening.

## 5) Реализация

- Вносить минимальные целевые изменения в существующую архитектуру.
- KISS: использовать самый простой уже существующий механизм.
- YAGNI: не реализовывать потенциальные будущие потребности.
- SOLID: разделять только реальные ответственности и внешние границы, не создавать слои ради паттерна.
- Новая dependency, конфигурация, service, database/table, queue, worker, storage-механизм, framework или общая abstraction требует одновременно:
  1. явного требования;
  2. доказательства, что текущий механизм не решает задачу проще.
- При отсутствии обоих условий новый механизм запрещён.
- Архитектурная замена допустима только при конкретном доказанном blocker для acceptance criteria; по умолчанию делать точечный hotfix.
- Комментарии в коде — на русском и только для неочевидной логики/причины; очевидный код не пересказывать.
- Кодировка UTF‑8, переносы строк CRLF (см. `.editorconfig`).

### Evidence gate для security

Security-изменение сверх уже очевидного минимального контура допустимо только при наличии цепочки:

`защищаемый актив → граница доверия → контролируемый источник/сбой → путь к sink → ущерб → недостаточность текущей защиты`.

Если цепочка не доказана применительно к реальной среде, отметить `ASSUMPTION — UNPROVEN` и не менять код.

### Stop-budget

До продолжения упростить решение, если один шаг:

- затрагивает больше 8 основных файлов;
- даёт больше примерно 1000 строк net diff;
- занимает больше 90 минут;
- требует новой подсистемы или заметно меняет архитектуру.

Если после упрощения запрошенный результат всё ещё недостижим, остановиться и задать пользователю один конкретный вопрос. Не создавать каскад новых шагов и не расширять команду агентов.

## 6) Проверка

- Сначала запустить targeted checks только для изменённой поверхности.
- После завершения всех изменений выполнить один итоговый gate, соразмерный риску (`typecheck`, `build`, связанные tests/smoke).
- Не повторять полный build/test без новых изменений.
- Проверить `git diff --check`, границы diff, UTF‑8 и CRLF изменённых текстовых файлов.
- Проверка должна доказывать `RESULT`, а не максимальное число гипотетических сценариев.

## 7) Итог в чате

В ответе пользователю обязательно:

- что сделано,
- какие файлы изменены,
- какой результат,
- какие риски,
- следующие шаги.

## 8) Отчёт по шагу (обязательно)

Создать файл: `.tmp/reports/step-XXX_<короткое-название>.md`

Отчёт краткий: только цель, фактический scope, результат, изменённые файлы, выполненные проверки и реальные оставшиеся ограничения. Не переносить в него весь ход рассуждений и не создавать из отчёта новый backlog.

Рекомендуемый шаблон:

```md
# Step XXX — <название>

Дата: YYYY-MM-DD

## Запрос / цель

## Понимание задачи

## План

## Сделано

## Изменённые файлы

## Команды (что запускалось)

## Риски / замечания

## Результат
```
